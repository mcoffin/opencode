# Built-in Tools

This is an inventory of the tools this harness (opencode) exposes to models, as implemented on the `mcoffin.v2-shell-squashed` branch. It covers the built-in tool plugins, the CodeMode meta-tool that wraps them, and the mechanism by which MCP-server tools are added dynamically. It does not cover slash **commands** (`ctx.command`) or VCS/websearch **provider** registrations, which are separate, non-tool-calling registries in the same codebase.

Tool registration, permission filtering, and execution all flow through [`Tool.Service`](packages/core/src/tool.ts) (see [`packages/core/src/tool/AGENTS.md`](packages/core/src/tool/AGENTS.md) for the architecture notes). Every built-in tool below is added via `ctx.tool.transform((draft) => draft.add({ ... }))` in its own plugin file under [`packages/core/src/tool/plugin/`](packages/core/src/tool/plugin/).

## Model-facing tools

The `Permission action` column is the string matched against `permission.rules[].action` (see [opencode.ai/v2/docs/permissions](https://opencode.ai/v2/docs/permissions/)); it is what a rule like `{"action": "edit", "resource": "*", "effect": "deny"}` in config actually targets. It is set two places that must agree: `options.permission` on the registration (used for whole-tool catalog visibility in [`Tool.Service.snapshot`](packages/core/src/tool.ts#L206-L211), `tool.options?.permission ?? name`) and the `action` field passed to `permission.assert({...})` inside the executor (the runtime check). Where a tool omits `options.permission`, both default to its own tool name.

## Notes on how the catalog is assembled

- **Registration and filtering.** All of the above (except MCP tools) call `ctx.tool.transform((draft) => draft.add({...})).pipe(Effect.orDie)` inside an `Effect.fn(...)` plugin body. Tool visibility per request is computed in [`Tool.Service.snapshot`](packages/core/src/tool.ts#L204-L253), which filters by permission rules and splits registrations into "direct" tools (`options.codemode === false`) and "codemode" tools (the default).
- **`patch` vs. `edit`/`write`.** These are mutually exclusive per model: a `context` session hook in [patch.ts:311-322](packages/core/src/tool/plugin/patch.ts#L311-L322) removes `edit`/`write` for non-`gpt-4`/non-`oss` GPT models and removes `patch` for everyone else.
- **`execute` (CodeMode).** Every tool registered with `options.codemode !== false` (the default for built-ins above) is *also* reachable from inside `execute`'s JS sandbox as `tools.<namespace>.<tool>(input)`, instead of being listed directly to the model. The sandbox additionally exposes a `search({query, namespace, limit, offset})` helper (see [`codemode/src/tool-runtime.ts`](packages/codemode/src/tool-runtime.ts#L75-L90)) for paging through the catalog rather than loading it all into context; the catalog itself is built in [`codemode/catalog.ts`](packages/core/src/codemode/catalog.ts) and its prose instructions in [`codemode/instructions.ts`](packages/core/src/codemode/instructions.ts). A tool opts out of CodeMode indirection (and is listed to the model directly instead) by setting `options.codemode: false`; every built-in leaf tool above does this, so in practice `execute` currently wraps only MCP-provided tools that don't opt out.
- **MCP tools.** [`tool/mcp.ts`](packages/core/src/tool/mcp.ts) discovers tools from connected MCP servers and registers one entry per tool, namespaced as `<server>_<tool>` (`McpTool.name`, [mcp.ts:16-17](packages/core/src/tool/mcp.ts#L16-L17)). Registration is redone on a debounced reload whenever the server reports its tool list changed ([mcp.ts:118-129](packages/core/src/tool/mcp.ts#L118-L129)), so this set is not fixed at build time.
- **`external_directory`.** A separate action, asserted by `read`, `write`, `edit`, `patch`, `glob`, `grep`, and `shell` (via `LocationMutation.externalDirectoryPermission`) whenever a resolved path — or, for `shell`, a directory referenced in the parsed command — falls outside the active Location. It gates crossing that boundary independently of the tool's own action, so denying `edit` doesn't imply denying `external_directory`, and vice versa.
- **Rule matching.** Per the [permissions docs](https://opencode.ai/v2/docs/permissions/), rules match `action`/`resource` with `*`/`?` wildcards and the *last* matching rule wins; this is implemented by `Wildcard.match` in [`util/wildcard.ts`](packages/core/src/util/wildcard.ts) and consumed in [`Permission.evaluate`](packages/core/src/permission.ts). A whole-tool `deny` on `*` for a given action removes that tool from the catalog entirely ([`tool.ts:259-262`](packages/core/src/tool.ts#L259-L262), `whollyDisabled`); anything narrower is enforced only at call time via `permission.assert`.
- **Shared types.** The `Tool.Info`/`Context`/`Result`/`Content` shapes every plugin builds against live in [`packages/schema/src/tool.ts`](packages/schema/src/tool.ts); the execution/definition helpers (`definition`, `execute`, `normalizeContent`) live in [`packages/core/src/tool/runtime.ts`](packages/core/src/tool/runtime.ts).
- **Non-tool registries (excluded above).** Slash commands (`init`, `review`, MCP prompts, user-defined commands) register through `ctx.command`, not `ctx.tool` — see [`plugin/command.ts`](packages/core/src/plugin/command.ts) and [`config/plugin/command.ts`](packages/core/src/config/plugin/command.ts). VCS backends ([`plugin/vcs/git.ts`](packages/core/src/plugin/vcs/git.ts), [`plugin/vcs/hg.ts`](packages/core/src/plugin/vcs/hg.ts)) and websearch providers ([`plugin/websearch/`](packages/core/src/plugin/websearch/)) similarly register into their own `ctx.vcs`/`ctx.websearch` drafts, not the model tool catalog.
